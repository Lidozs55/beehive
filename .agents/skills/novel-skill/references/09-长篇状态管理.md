# 09-长篇状态管理

## 模块定位

本模块管长篇协作中的可检索记忆、连续性、接管与修改同步。它不规定项目必须使用某套目录，也不要求每章刷新所有文件。

核心原则：状态系统应随真实风险增长。先建立最小状态集；只有当信息数量、协作者或连续性风险证明需要时再拆分。项目已有文档地图时，以项目地图为唯一结构权威。

## 一、状态的三档规模

### 轻量状态

适合短中篇、单会话章节组或刚开始的项目。一个文件或结构化区块即可，包含：

- 当前进度与下一步。
- 主要人物当前状态和信息边界。
- 开放问题、承诺或伏笔。
- 已确立且容易冲突的事实。

### 标准状态

适合持续多章协作、群像或规则复杂的长篇。可按项目结构拆分：

- `handoff`：当前进度、近期变化、下一步和风险。
- `character-state`：人物位置、身体、关系、目标、已知与误信。
- `open-threads`：开放悬念、伏笔、承诺及预计处理窗口。
- `facts`：正文已确立的规则、事件和物品状态，带来源位置。
- `summaries`：章节或故事弧的差分摘要。

### 扩展状态

只有出现实际需求时再增加：剧情线相位、时间线、空间布局、资源账、术语表、风格说明、桥段记录、多世界或试炼状态等。对应机制不存在时，不创建空表。

## 二、最小章节循环

章节循环可按请求裁剪：

1. **校准**：读取交接信息、上一章关键段、本章人物和开放线索。续写语感时原文优于摘要；查事实时状态优于凭印象。
2. **定向**：明确本章核心变化、人物选择、与前文接口。用户只要正文时不必展示内部清单。
3. **起草与修订**：依任务加载相关工艺模块，不在每段写完后执行全套审计。
4. **同步变化**：记录本章实际改变的事实、人物状态、开放线索与下一步。没有变化的文件不刷新。

同步完成度由后续使用风险决定。临时试写可以不进入正式状态；已确认或发布的章节应及时同步。

## 三、信息所有权

同一事实尽量有一个规范来源：

- 世界圣经存“设计上应当成立的规则”。
- 正文存“读者实际看见的表达与事件”。
- 状态文件存“当前可供写作检索的摘要与运行状态”。
- 大纲存“尚未落地的计划”。

发现冲突时不要机械执行固定优先级。先判断它是正文笔误、设定已演化、摘要过期还是大纲失效；再选择修正文稿或反向同步，并记录裁决。已发布正文通常具有较高变更成本，但不因此自动把明显笔误升级成世界规则。

## 四、关键状态字段

### 交接信息

只保留能让下一次工作正确启动的内容：最后确认位置、当前场景或故事弧、近期重大变化、下一步意图、开放风险、用户明确否定的写法。

交接不是全书摘要，不复制其他文件的完整内容；用引用或编号指向规范来源。

### 人物状态

按近期相关人物记录：

- 位置、身体和情绪基线。
- 当前目标与下一步意图。
- 与关键人物关系的最近变化。
- 已知信息、信息来源、不知道的事、相信但错误的事。
- 携带或控制的重要物品与资源。

静态人物档案与当前状态分开：前者描述较稳定的动机、声音和行为倾向；后者描述“现在怎样”。

### 开放线索

每条记录内容、首次出现位置、当前状态、相关人物、预期处理范围和下一次可能动作。处理范围可写成场景、弧线或卷，而非强制精确到章节。

开放线索数量和沉默时长只作为注意力信号。判断是否失控，要看读者是否仍能记住、文本是否仍承诺处理、以及该线是否有意休眠。

### 既定事实

只记录后续可能依赖、容易记错或已发生冲突的事实。每条带正文位置或确认来源。不要把每个普通动作都抄进事实表。

### 摘要

摘要记录变化，不复述百科：谁做了什么选择，局势、关系、信息或资源因此怎样变化，哪些承诺开启或关闭。

可在自然边界生成滚动摘要，例如故事弧结束、上下文过长或准备换会话时；不要求固定每若干章生成。

## 五、加载策略

写作前只加载足够支撑当前任务的材料：

1. 当前交接与用户本次要求。
2. 上一章或相关场景原文。
3. 本章涉及人物的当前状态与稳定档案。
4. 与本章有关的开放线索、规则、时间或空间条目。
5. 当前故事弧的大纲。

不整体加载与本章无关的全书资料。材料太长时，先按人物、线索或时间检索，再读取命中处周边上下文。

## 六、项目结构

本 skill 不指定通用目录。执行顺序是：

1. 寻找项目现有的总览、README、文档地图或用户说明。
2. 识别现有文件分别拥有哪类事实。
3. 优先扩展现有规范文件，不创建同义文件。
4. 只有职责独立、更新频率不同且已有真实内容时才拆文件。
5. 把新文件加入项目既有地图；项目没有地图且规模很小时，不为此新建一份。

概念名如 `handoff`、`facts`、`outline` 只是职责，不是要求使用的路径或英文文件名。

## 七、已有书稿接管

接管遵循“声明范围、先读后断言、分批建模”：

1. 明确用户要续写、局部改写还是整体诊断，以及不可动项。
2. 读取用户指定文本与必要的前后缓冲。材料很长时可分批阅读并逐步提取状态。
3. 清楚声明已读范围；在全文未读完前可以给局部发现，但不得把抽样结论冒充全书结论。
4. 从正文反推人物声音、实际规则、时间线、开放线索和结构，而不是强迫旧稿适配本 skill 的模板。
5. 先给近期可执行路线；只有持续协作需要时才建立完整状态系统。

同人接管还需区分原作已确立、原作暗示和可自由扩展区域。

## 八、修改与反向同步

当正文或设定发生实质修改时：

1. 确定变化影响的人物、时间、规则、物品、线索和后续章节。
2. 修改规范来源。
3. 更新依赖该事实的状态摘要与大纲。
4. 检查后文是否仍引用旧版本。
5. 保留必要的变更理由；无需为每个措辞调整建立日志。

已发布内容与新设定冲突时，应向用户说明修改旧章、仅对未来生效或解释为设定内变化的代价，让用户决定高影响取舍。

## 九、连载与完结稿

- **连载**：已发布内容回改成本高，开放线索与事实应及时记录；近期规划更具体，远期规划保留弹性。
- **完结稿**：允许全书重排与回填，状态可按故事弧阶段性更新；集中修订后再统一重建摘要与事实。
- **探索稿**：允许写作发现故事，只记录已确认内容；不要把试写假设过早固化成规则。

模式可切换，但切换时应明确哪些内容已发布、哪些仍可自由修改。

## 十、健康检查

在自然阶段边界检查：

- 是否有角色知道自己无法获得的信息？
- 伤势、物品、位置、时间和资源是否连续？
- 开放线索中是否有已经失去叙事意图的条目？
- 大纲是否仍描述真实方向，还是已被正文淘汰？
- 重要配角、关系或主题是否因遗忘而消失？
- 状态文件是否出现重复所有权、过期内容或维护成本高于价值？

状态系统的目标是减少错误与恢复成本。若记录动作没有被后续检索使用，应合并、降低频率或删除，而不是继续扩建。
